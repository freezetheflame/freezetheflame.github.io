## 先想清楚：业务岗考的不是论文

我把它压缩成一句话：**你改了什么、指标动了多少、代价是什么、怎么证明不是噪声。**

研究和业务的差别不在“模型高不高级”，而在**约束**：业务方有供给上限、有延迟预算、有生态规则、有审核压力，任何一个改动都要在 AB 里证明自己。所以准备的重点不是多读几篇论文，而是**攒出一条能讲完整因果链的项目**。

三个必须先内化的“业务真相”：

1. **离线涨 ≠ 线上涨**。样本偏差、位置偏差、特征穿越，任何一样都能把离线 AUC 的提升变成线上的负收益。
2. **模型不是唯一杠杆**。重排打散、多样性配额、生态扶持，在真实业务里经常比换模型收益更大。
3. **冷启动和成本决定天花板**。新用户/新 item 怎么活、QPS 乘以延迟再乘机器成本能不能扛，比“用了什么结构”更常被追问。

## 一、先选赛道：四类岗位

| 岗位 | 日常 | 需要的能力 |
|---|---|---|
| 推荐算法（召回/排序/多目标） | 建模、特征、离线评估、AB | 模型 + 指标感 + 实验设计 |
| 推荐系统工程/后端 | 特征平台、训练/推理链路、延迟、存储 | 分布式、性能、稳定性 |
| 生态/风控/内容安全算法 | 作弊检测、生态治理、评价体系 | 对抗评测、指标设计、系统视角 |
| LLM4Rec / 生成式推荐 | 生成式召回、语义 ID、Scaling | 模型 + 大规模训练 |

我的打法是**主打“系统工程 + 生态治理”，算法能力作为第二条腿**：这条路人少、竞争不挤，而且“会评测 + 会压延迟”是稀缺组合。

## 二、知识地图（四层）

### 第 1 层：模型——要能白板上推出来

- 协同过滤 → 矩阵分解 → **FM / FFM** → **双塔（DSSM）**
- GBDT + LR（要能解释它为什么被深度模型取代）
- 排序：**DIN / DIEN / SIM**（长序列）、**MMoE / PLE**（多任务）、**ESMM**（CVR 的样本选择偏差）
- 序列：**SASRec / BERT4Rec**
- 召回：i2i / u2i、向量检索（Faiss、HNSW）、**语义 ID（TIGER）**
- 重排：DPP / MMR（多样性）
- 前沿：**HSTU**（Meta 的生成式推荐）、**OneRec**（快手，统一召回与排序）

判断标准不是“知道名字”，而是能在白板上画出结构图，并说清**它解决了上一个方法的什么缺陷**。

### 第 2 层：系统——要能画链路图

- 全链路：日志 → 样本拼接 → 特征 → 训练 → 模型服务 → 召回/粗排/精排/重排 → 返回
- **特征平台**：离线、近线、在线三份特征如何保证一致（这是工程岗最高频的追问）
- 训练：大规模 embedding（PS/worker）、稀疏梯度、增量训练
- 推理：延迟预算（看 P99，不看均值）、批处理、量化/蒸馏、降级、缓存
- 向量检索：索引选型、召回率与延迟的权衡、增量更新

### 第 3 层：业务与实验——要能算账

- 指标：AUC / **GAUC**、NDCG@k、HR@k、覆盖率、多样性、时长、GMV、留存
- **AB 实验**：分流、样本量、CUPED 方差缩减、多重比较、新奇效应与长期效应
- 冷启动、探索利用（ε-greedy / UCB / Thompson）、供给约束、生态配额
- 偏差：位置偏差与去偏（PAL、蒸馏）、样本选择偏差（ESMM 的思路）

### 第 4 层：前沿——加分，不是必需

生成式推荐、LLM 做特征与召回、长序列建模、推荐系统的 Scaling。面试里能提一句“我看到 HSTU 把推荐当序列生成任务”，就够了。

## 三、必读清单

书两本：王喆《深度学习推荐系统》（业务视角最好的一本）、项亮《推荐系统实践》（老，但当历史读）。

论文十篇，按顺序读，每篇只回答一个问题：

| 论文 | 读完要能回答 |
|---|---|
| YouTubeDNN (2016) | 工业界两阶段召回+排序的骨架长什么样 |
| DIN (2018) | 为什么要对用户历史做 attention，而不是直接 pooling |
| DIEN (2019) | 兴趣为什么会漂移，GRU + attention 怎么建模 |
| SIM (2020) | 长序列（上万条）怎么在延迟内用起来 |
| SASRec (2018) | 序列推荐为什么能用 Transformer 做 |
| MMoE (2018) | 多目标为什么会互相拉扯，门控怎么分 |
| PLE (2020) | MMoE 的跷跷板效应怎么缓解 |
| ESMM (2018) | CVR 训练样本缺失怎么用全空间建模 |
| TIGER (2023) | 语义 ID 怎么把召回变成生成 |
| HSTU (2024) | 把推荐当序列生成任务，和传统范式差在哪 |

## 四、四个项目

### 项目 A：端到端两阶段推荐（4 周，必须有）

- 数据：Amazon Beauty（更接近电商业务）或 MovieLens-1M
- 链路：多路召回（双塔 + i2i 协同 + 热门兜底）→ 精排（DIN）→ 重排（DPP 多样性）
- 必须做的细节：**全库评估**（不是负采样评估）、GAUC、覆盖率、P99 延迟
- 交付：repo + README，写清“每个决策为什么、指标动了多少”
- 面试怎么讲：先说约束（数据量、延迟预算），再说取舍（为什么双塔而不是交叉特征），最后说结果与失败尝试

### 项目 B：一个真实业务问题（2 周）

选**冷启动**：新 item 的曝光怎么分配。搭一个 bandit 模拟器（用户响应模型 + 曝光反馈），对比 ε-greedy / UCB / Thompson，报三个数：新 item 的 7 日 CTR、曝光占比、整体 NDCG 的损失。

这个项目的价值在于它是**有取舍的**：探索必然损害短期指标，业务方关心的正是“损失多少、换回多少”。

### 项目 C：系统化（2 周）

FastAPI + Faiss + Redis 特征，做三件事：压测 P99、杀掉一个依赖演示降级、写一个特征一致性检查脚本（离线特征与在线特征逐字段比对）。

这一段直接对上系统工程岗，也是面试里最能体现“你上过生产”的部分。

### 项目 D：差异化（可选，2 周）

做**推荐系统的鲁棒性评测**：注入/投毒检测，或 LLM 推荐 agent 的记忆污染测量。对口生态治理、内容安全岗，而且绝大多数候选人没有这个视角。

## 五、12 周执行表

### 第 1–2 周：地基

- [ ] 读 YouTubeDNN、DIN、SASRec，各写 300 字笔记（解决什么问题 / 结构 / 指标）
- [ ] 下载 Amazon Beauty，用 RecBole 跑通 BPR baseline
- [ ] 记录基线数字：HR@10、NDCG@10（这是后面所有对比的原点）

### 第 3–4 周：项目 A 主体

- [ ] 双塔召回训练 + Faiss 建索引，实现全库评估
- [ ] DIN 精排，复现论文里的 attention 结构
- [ ] 对比：热门召回 / i2i / 双塔，报 Recall@50、Recall@200

### 第 5–6 周：消融

- [ ] 序列特征（最近 N 次交互）加与不加的对比
- [ ] 负采样比例对排序指标的影响（并解释为什么采样评估会骗人）
- [ ] MMoE 或 PLE 加一个辅助目标（如点击 + 时长），看是否跷跷板

### 第 7–8 周：项目 B

- [ ] 写 bandit 模拟器（用户偏好 + 噪声 + 曝光反馈）
- [ ] 跑 ε-greedy / UCB / Thompson 三组，产出“探索率与长期收益”曲线
- [ ] 写一页结论：什么条件下该多探索

### 第 9–10 周：项目 C

- [ ] 在线服务：召回 + 排序串起来，压测 P99
- [ ] 降级：向量库不可用时回落到热门
- [ ] 特征一致性检查脚本，找出至少一处偏差

### 第 11 周：整理

- [ ] 三个 repo 的 README 改写成“问题—方案—指标—反思”
- [ ] 简历改成一页，每条经历都带数字
- [ ] 把 12 周的失败记录整理成一页（面试最爱问“你踩过什么坑”）

### 第 12 周：面试冲刺

- [ ] 手撕：LR、GBDT、Attention、负采样、Top-K 堆、AUC（含并列）
- [ ] 系统设计：白板画一遍“首页推荐系统”
- [ ] 业务 case：准备三个（留存下降、多样性下降、AB 不显著）

## 六、面试四类题

### 1. 手撕

LR 与 GBDT 的推导、Attention、负采样、Top-K 用堆、AUC 计算（并列分数怎么处理）。这些是门槛题，答错直接出局。

### 2. 系统设计

“设计一个首页推荐系统”是必考题。答题顺序：

1. 先问约束：日活多少、QPS、延迟预算、有没有冷启动压力；
2. 画链路：多路召回 → 粗排 → 精排 → 重排；
3. 讲一致性：特征离线/在线怎么对齐；
4. 讲降级：依赖挂了怎么办；
5. 讲实验：怎么验证改动有效。

**画图 + 讲取舍**，不要背结构。

### 3. 业务 case

“新用户次日留存掉了 3% 怎么排查”这类题，答法是固定套路：

1. 分层拆解（人群、场景、端、供给）；
2. 提出假设（新用户变多导致冷启动占比上升？某个渠道质量下降？）；
3. 说清需要什么数据（漏斗、分渠道留存、供给覆盖率）；
4. 给验证方案（灰度、AB、样本量与观察周期）；
5. 说风险（指标互相拉扯、长期效应）。

### 4. 八股清单

- GAUC 和 AUC 的区别，为什么线上看 GAUC
- 负采样比例怎么选，采样评估为什么虚高
- 位置偏差怎么产生、怎么去偏（PAL / 蒸馏）
- 特征穿越与样本泄漏的典型例子
- 实时特征与离线特征不一致会怎样
- embedding 冲突、哈希冲突怎么处理
- 多目标融合：加权、约束、Pareto 各适合什么场景
- 冷启动的三条路：内容侧、探索、迁移
- 延迟预算怎么拆（召回/排序/网络/序列化）
- AB 不显著时怎么办（功效不足、指标选错、长期效应）

## 七、简历怎么写

对比一下同一件事的两种写法：

> 差：基于 DIN 实现了推荐排序模型，提升了效果。

> 好：在 Amazon Beauty 上实现双塔召回 + DIN 精排，全库评估 HR@10 从 0.xx 到 0.xx；推理 P99 从 xx ms 降到 xx ms（批处理 + 量化）；上线前做特征一致性校验，发现并修复 3 处离线/在线偏差。

差别不在技术，在于**有没有数字、有没有规模、有没有代价**。

## 八、两个差异化优势

1. **Infra 能力**：推理优化、延迟与成本、批处理、加速器后端。业务方最缺“能把模型压进延迟预算的人”。
2. **评测与安全**：会设计指标、会做对抗评测、懂注入与投毒。生态治理、内容安全算法岗的候选人里，受过系统评测训练的人极少。

这两条不需要额外包装，只要在项目里真的做过，写出来就是差异。

## 九、这周就动手的三件事

1. 读 YouTubeDNN 和 DIN，各写 300 字笔记；
2. 下载 Amazon Beauty，用 RecBole 跑 BPR，记下 HR@10 与 NDCG@10 当基线；
3. 决定项目 A 的数据集与延迟预算（比如 P99 小于 100 ms），把它写进 README 第一行。

## 十、几个坑

- **只做模型不做系统**：面试一问特征一致性就露馅；
- **只报离线指标**：没有代价和延迟的指标，业务方不信；
- **项目没有失败记录**：讲不出踩过的坑，说明没真跑过；
- **追新模型**：HSTU、OneRec 是加分项，不是主线，基础不牢时读它们只会更慌。

计划是给人用的，不是给人看的。12 周里允许两周掉链子，但**项目 A 必须完整跑完一遍**——它是所有面试话题的载体。
